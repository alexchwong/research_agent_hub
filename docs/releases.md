# Release verification

The fixture setup workflow exercises the installed wheel, selected platform shortcut, a failed core-app installation and a scoped retry. The pinned upstream workflow exercises the standard packaged manifests, all three real installs, native browser readiness, GPT Researcher’s origin protections, PaperQA2’s synthetic request serialization and native LDR RIS intake.

Ubuntu 26.04 x64, Apple silicon macOS 15 and Windows Server 2025 x64 are the GitHub Actions targets. Complete the desktop and live checks below before publishing 0.1.0.

Package from a clean source checkout or export. Exclude `.venv/`, `build/`, `dist/`, `.release-test/`, `reports/`, caches and populated `.env` files from source deliverables. CI retains the fixture and packaged smoke JSON reports separately from the bootstrap bundle. A credential-free report does not establish live-provider or desktop qualification.

## v0.1.0 evidence checklist

For each advertised OS version and architecture, record the wheel hash, app pins, manifest and lock hashes, Python/uv versions, and the report or checklist reference. Mark each check **passed**, **failed**, or **not run**. Do not carry results forward to a changed pin or artifact route without rerunning the affected checks.

| OpenRouter usage and native app mappings | Explicit live opt-in and authorized credentials; no interactive test prompts | Compare Usage with the current-key response. Confirm role overrides and native control in actual pinned upstream runs; the direct API smoke is not enough. |

Capture only sanitized evidence: no API keys, raw provider payloads, private paths, or PDF contents. Escalate a blocked host or route before narrowing release scope. See [DEVEL.md](../DEVEL.md) for build and live commands.

## Desktop and CI checks

1. Run **Cross-platform setup** and **Pinned upstream setup** on Ubuntu 26.04 x64, Apple silicon macOS 15 and Windows Server 2025 x64. Both workflows build a fresh wheel. The latter installs the packaged app pins and starts the real upstream browsers. Run the commands in [DEVEL.md](DEVEL.md) locally if a runner fails. Capture OS, architecture, Python/uv versions, manifest digests and the failing step.
2. On Windows 11 x64, Apple silicon macOS and Ubuntu x64, boot from the installed shortcut on a clean test user, approve the core plan and open both native UIs. Check authenticated LDR setup and native exports, GPT Researcher history and reports, and the PaperQA2 standalone command and managed eligibility visible in the dashboard. Confirm port conflicts, browser restart and setting changes are reported, and prove retained standalone browser and CLI use after hub-only removal. The Windows Server runner does not establish Windows 11 desktop acceptance.
3. Check the native platform prerequisites. The install needs disk space for three separate venvs and the uv cache. Use a disk-backed temporary directory for combined smoke tests. Verify Windows private ACL inheritance and long-path support if archive extraction fails. macOS 14 or later is required by the pinned arm64 FAISS wheel. Verify desktop libraries and export dependencies separately. Native PDF rendering may need WeasyPrint system libraries. Confirm LDR's SQLCipher and initial resource use on each target.
4. Before marking install routes supported, review the locked wheels and bundled source-built packages per host, native first-run downloads and upstream notices. Confirm extra model and search integrations against the agreed base scope. The source-archive and wheel licence records for GPT Researcher differ and both need redistribution review.


## Managed PaperQA2 enablement

The earlier Linux x64 report established scoped chat transport (Azure on 10 observed chat generations) and a native cited answer. Its settings came from diagnostic defaults and the embedding result did not identify its onward provider. The release manifest stays closed while these gaps are open.

1. Run the installed-hub command in [DEVEL.md](../DEVEL.md) for each target under review. Check saved/applied roles, the selected corpus and prior index isolation, consent rejection, the native answer and citation, both pinning negatives and expected request origins. Verify endpoint catalogue evidence for embeddings. A successful strictly constrained route with a paired routing-specific negative can establish the eligible embedding provider even when downstream embedding identity is unobservable. Record that limitation.
2. On each candidate host, supplement the Python observation with independent host or process network observation for the disposable run. Record scope and whether additional traffic was observed. Compare Usage against the current-key response and exercise actual LDR and GPT Researcher role mappings using test credentials. Complete an LDR literature survey through RIS/manual review, user-supplied PDFs and native PaperQA2 output.
3. Review the JSON and record its reference, host, worker and lock identities. Promote its candidate record to `verified` only after the checks pass and update only the matching trusted row in `rah/install_assets/routes.json`. Account ZDR is optional. Adding request-level policy changes needs a separate live check. Repeat the installed-hub command against the final package with the normal manifest and confirm that the report says the packaged gate was enabled.
4. Record the exact LDR and GPT Researcher model defaults only after each role's live adapter check. Keep native selection available when no recommendation has passed. Publish only desktop ZIPs accepted on the actual stated host. Release workflow artifacts and checksums are candidates until that check is done.
